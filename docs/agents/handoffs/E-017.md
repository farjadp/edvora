# E-017: Object storage (S3 / ArvanCloud) + copying live-class recordings

**Agent:** tech-lead · **Date:** 2026-11-07 · **Branch:** `feature/storage-e017` (stacked on `feature/live-classes-e033`)

1. **Task:** board E-017, the S3 storage adapter (local S3 / ArvanCloud in production) for Media. Farjad asked for it
   to finish D4 of E-033: copy live-class recordings into our own storage.
2. **Output:**
   - `packages/integrations/src/storage/`: the `ObjectStorage` interface, an S3 adapter (AWS SDK v3, path-style,
     explicit keys, multipart uploads, signed GETs), an in-memory mock, `objectKey()` with tenant-first,
     traversal-proof keys, `ensureS3Bucket`, and tests, including an opt-in real round trip.
   - `apps/web/src/lib/liveRecordings.ts`: streams provider MP4 → bucket, idempotent, with status
     `ready / waiting / copying / copied / failed` and the error stored.
   - `GET /live/[id]/recording/[rid]`: enrolled student of the cohort, or the host → 303 to a 5-minute signed URL.
     Anyone else gets 404, or 401 when signed out.
   - `POST /live/[id]/recording/[rid]/copy`: the host retries a copy.
   - UI: «تماشای ضبط» on the course page; recording status and «کپی دوباره» on `/staff/teaching`.
   - Media in S3 through `@payloadcms/storage-s3`, gated by `S3_MEDIA=true`. Local disk stays the default.
   - Migration `20261107_032956_e017_recording_storage` (new columns on `live_sessions_recordings`).
   - Local S3: SeaweedFS replaces MinIO in `compose.local.yml`, with auth on. Runbook `docs/runbooks/object-storage.md`.
3. **Decisions made:**
   - **SeaweedFS for local dev:** `minio/minio` and `quay.io/minio/minio` both refuse pulls now.
   - **Checksums only `WHEN_REQUIRED`:** the SDK's default CRC32 on every request breaks some S3 clones.
   - **Recordings are not lessons:** lessons are course-wide, but D4 needs cohort-only visibility. Recordings stay on
     the session and are played through a checked route. A lesson can link to them later.
   - **Copying runs in `after()`** (after the webhook response), because there is no job worker yet (E-016).
4. **Open issues:**
   - No per-student watermark on recordings yet; it needs the protected player (phase-2 B). The signed link gives
     the plain file.
   - No automatic retry for `waiting` / `failed`: the host retries by hand until E-016.
   - Not tested against ArvanCloud itself, only against S3-compatible SeaweedFS with signatures on. Check on first
     deploy: a multipart upload over 1 GB, and a signed GET from an Iranian mobile network.
   - Existing local Media files aren't migrated automatically when `S3_MEDIA` is turned on (runbook §5).
5. **Next owner:**
   - **devops:** the Arvan bucket and keys.
   - **qa:** the recording flow on the trial BBB server.
   - **tech-lead:** E-016 worker for automatic retries.
