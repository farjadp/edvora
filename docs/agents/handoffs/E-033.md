3. **Decisions made:**
   - **Recommend build on open source: BigBlueButton 4.0, self-hosted in Iran.** It is the only option covering every D
     story natively, including attendance and recording callbacks. It is legal (LGPL) and very active, with an RTL
     Persian UI and free per-meeting branding. Score 84/100. It stays first when any single weight is doubled.
   - **Shortlist: BBB self-hosted and Skyroom.** Skyroom (73) is the only legal, credible buy option. Its API has no
     webhooks, attendance or recordings, it deletes recordings after the service ends, and white-label is paid per tenant.
   - Wider sweep (Farjad asked for more): **plugNmeet** (76, MIT, BBB-compatible API, fa + RTL) is **plan B**. It does
     not displace BBB: bus factor 1, Docker Hub/Google install chain, load test with simulated users only. OpenTalk
     (61) and La Suite Meet (51) lack Persian and RTL.
   - Webinars over 200: BBB → RTMP bot (THM-Health/BBB-Streaming-Server) → MediaMTX LL-HLS at 480p (≈ 0.5 Gbps for
     500), or a Skyroom day pass.
   - Managed BBB from an Iranian host (79) uses the same adapter: a **stop-gap if the server is late**, or the backup
     link. LiveKit (72) is noted for a future native classroom.
   - **Rejected on gates:** Adobe Connect resellers (cracked builds, said by the reseller), OpenVidu PRO and MiroTalk's
     commercial licence (Stripe or phone-home).
   - The adapter returns `expiresAt: null` for BBB, because its join URLs don't expire while the meeting runs. The join
     route (303, ADR 005) is the real gate.
   - `externalRoomId` = `<tenantId>:<liveSessionId>`. Webhook tenant resolution order: session lookup, then the
     tenant's credentials, then verify, then match.
   - The mock keeps process-wide state with deterministic room ids, so a per-request factory works. Zod validates at
     the boundaries.
   - The `tech-lead` review's must-fixes are all applied: lazy create + `createTime`, ticket expiry, N recordings per
     session, webhook tenant order, LiveKit needs a client page.

## Phase 3: proof of concept (approved by Farjad 2026-11-06, "Start phase 3")

**Output:**
- **BBB adapter:** `packages/integrations/src/live-class/bigbluebutton.ts` plus 30 tests. It covers:
  - checksum API, create (idempotent), signed join URL, end, meeting info and recordings
  - webhook parsing for bbb-webhooks, the recording-ready JWT, the analytics callback (HS512 JWT) and a signed meetingEnded URL
  - a small XML parser that rejects DOCTYPE; no new dependency
- **Core:** `packages/core/src/live.ts` plus 10 tests. It covers the join window (opens 10 min before, closes 30 min
  after the end), the host starting 30 min early, room ids `<tenantId>:<sessionId>`, the 24 h replay guard, and
  attendance merging (intervals, end-of-class summary wins, manual corrections are kept).
- **Data:** collections `live-sessions`, `attendance` (unique on session + user) and `live-events` (unique on tenant +
  provider + eventId), all tenant-scoped. Migration `20261107_052440_e033_live_classes_storage` (re-created after e032 when merging develop), applied cleanly on an empty DB.
- **Routes:**
  - `POST /live/[id]/join` (student, 303)
  - `POST /live/[id]/host` and `/end` (host, 303)
  - `POST /live/webhook/[provider]`
  - `/live/mock` + `/live/mock/leave`: the offline classroom for dev and demo
- **UI:** a "کلاس‌های زنده" block on `/learn/[course]`, and the host's list with start/end buttons on `/staff/teaching`.
- **Ops:** `docs/runbooks/bigbluebutton.md` (Iranian VM, mirrors, TURN/443, settings that keep it inside Iran,
  webhooks, pilot checklist). Dev data: `src/seed/e2e-live.ts`.

**Checked by hand (curl against the dev server, demo tenant, separate DB `edvora_e033`):**
- Student before the host starts → `?live=not-started`.
- No session → login. Other academy's host → login. Student on the host route → 404.
- Host starts → status `live` → mock room as moderator.
- Student joins → attendance row; a reload adds no second row (deduped); leaving records `leftAt`.
- Host gets no attendance row (not enrolled).
- Forged webhook → 401; wrong provider → 404.
- Host ends → `ended`; a later student join → `?live=ended`.
- The server log had no errors.

**Decisions made:**
- A local docker-compose for BBB was not built: BBB 4.0 needs a clean Ubuntu 24.04 server with public UDP, and it
  doesn't run on macOS Docker. Dev and CI use the mock, which goes through the same `ingestEvents` path as real webhooks.
- One BBB server per Edvora instance, set in env (`LIVE_CLASS_PROVIDER`, `BBB_URL`, `BBB_SECRET`), shared by its academies.
- Students can join only after the host has started (status `live`). This covers D8: no one sits in an empty room.
- Attendance is recorded only for students enrolled in the course; hosts and others are ignored.

**Open issues:**
- **D4 copy step not built:** recordings are listed on the session, but copying them to Arvan S3 and attaching a
  lesson waits for the S3 adapter (E-017).
- **Not yet built:** D1's overlap warning, D6's reschedule notification (module F), and D7 webinars.
- **Not run against a real BBB 4.0 server.** Check on the trial VM:
  - bbb-webhooks version must be **≥ 3.4.0** (older versions sign `"{}"`, not the body).
  - The `video` format is enabled, and MP4 shows up after `presentation` is published.
- **Replay limits:** the analytics callback's JWT doesn't cover the body, and the recording-ready JWT never expires.
  Both are mitigated by permanent dedupe and by matching each event to a stored session; the residual risk is noted.
- **Migration order:** PRs #17, #19 and #21 may also add migrations. Whoever merges second regenerates the migration
  (`payload migrate:create`) after rebasing.
